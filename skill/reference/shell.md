# 交互式 shell：交付标准与降级规则

拿到 RCE 不等于交付完成。用户通常想**自己敲命令**，所以按下面的优先级走，
并且**降级必须坦白**。

## 优先级

| 优先级 | 形态 | 何时用 | 代价 |
|---|---|---|---|
| 1 | **持久 webshell / 反向 shell** | 目标存在可写且可访问的目录，或可回连 | 毫秒级/命令 |
| 2 | 逐命令 RCE | 拿不到持久通道 | 每条命令重跑一次利用 |

## 判据：能不能落持久 shell

先看这两件事，缺一就只能降级：

1. **可写**：目标上有可写目录（`preflight --container X` 会列出候选）
2. **可访问**：这个目录同时能被 Web 访问，或能从容器回连出来

> 「可写」≠「可访问」。曾经遇到 docroot 是 `:ro`、只有 `/out` 可写的靶场，
> 那里只能"写文件 + 读文件"，拿不到持久 shell。

## 交付前必须验证

不要只看"文件写成功了"。**跑一条 `id` 看回显**，确认 shell 真的能应答。

```bash
# 反例：只检查部署成功
# 正例：
curl -s 'http://TARGET/pwn.php?c=id'   # 必须看到 uid=
```

## 降级时的标准措辞

必须让用户知道差额，不能含糊：

```
无持久 webshell 可用，改用逐命令执行 —— 每条命令会重跑一次利用，
不保留 cd / 环境变量
```

## 已修复的目标不给 shell

修复对照本来就不该有通道。给出一个"能用"的 shell 等于伪造结论，
比不给更糟。接口应当明确拒绝并说明原因。

## 清理是义务

会话结束、重启、异常退出都要移除落下的 shell 文件。

- bind mount 场景下，文件会留在**宿主仓库目录**里，容易被误提交
- 启动时扫一遍上次的残留
- 清理脚本只删自己命名空间的东西（前缀匹配），不要宽匹配
  （`pkill -f server.js` 这类会误伤无关进程，这是真实踩过的坑）

## 不是完整 PTY

逐命令模式没有 `cd` / 环境变量持久，`top`、`vim` 这类全屏交互不可用。
若用户要求真会话，用目标语言的原生手段（如 `php -a`、`/bin/sh -i` 反弹）。

## 记录到 dashboard

案例 JSON 的 `demo.shell` 要写清档位，让用户在点开前就知道会得到什么：

```json
"shell": { "kind": "webshell", "available": true,
           "note": "持久 webshell：命令毫秒级，但 cd/env 不跨命令保留" }
```
