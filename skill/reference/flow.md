# 流程细节：检查点、产出物、失败回退

主流程见 [../SKILL.md](../SKILL.md)。本文件是每阶段的执行细节。

---

## S1 线索归一

**输入形态**：CVE 编号 / GHSA / 补丁 commit / 一句模糊描述（"某产品后台可能有洞"）。

要做的事：

1. 找到**权威来源**：官方安全公告、修复提交 diff、NVD/GHSA 条目。至少两处交叉。
2. 抽出版本区间：受影响区间、修复版本（按分支列，不要只记一个号）。
3. 判断缺陷层级：内存安全？逻辑？配置？——这决定 S4。

**产出**：来源列表（带 URL）+ 受影响/修复版本表。

**回退**：找不到公开细节时，直接以补丁 diff 为准。**没有 diff 就不要猜利用方式**，转而做黑盒探测或明确报告"信息不足"。

> 案例一的做法：拿到修复提交 `31c0ea7d` 的 diff（`Zend/zend_alloc.c` +527/−124），
> 从 `longjmp` → `UnwindExit` 的改动直接推出根因与触发面。

---

## S2 产品/版本矩阵

目标：找到**真实承载该组件的产品**，并锁定"组件未修复、且镜像可获取"的版本。

### 最大的坑：latest 已经修了

官方镜像在漏洞公布后常**重建所有标签**，把组件悄悄升到修复版。
案例一实测：WordPress / Drupal / MediaWiki / Joomla / phpMyAdmin 的 latest
内置 PHP **全部恰好等于修复版本号**，全军覆没。

所以：

- 必须找**构建日期早于修复公布日**的旧标签
- 记录每个 tag 的构建时间与内置组件版本**作为证据**
- 判定"不可用"前先确认不是标签被重建导致的假阴性

### 常见获取路径

| 路径 | 适用 |
|---|---|
| 产品自带多版本标签（`wordpress:6.8-php8.4-apache`） | 首选 |
| 官方基础镜像 + 应用源码叠加 | 产品无对应组件版本标签时（案例一的 MediaWiki / phpMyAdmin） |
| 源码包 + 自行构建 | 需要特定补丁级别时 |

**产出**：产品 × 版本 × 组件版本表，标注"可获取/不可获取"。

## S3 镜像获取

- 拉取后在容器内**核实组件真实版本**（`php -v`、包管理器、`/proc/<pid>/maps`），不要相信标签名。
- 记录镜像 digest、构建时间、内部版本——这是"我打的是哪个版本"的唯一凭据。
- 需要符号/偏移时，从目标容器内提取（案例一：`docker cp <c>:<libphp.so>`）。

**回退**：镜像拉取失败/超时，记为"未能评估"，**不要**算作"不可利用"。案例二里
Monica、EMlog、Typecho 都属此类，错误地被归为否定结论会污染最终判断。

---

## S4 前提判定（最关键的一步）

问两个问题：

1. 这是**组件自身**的缺陷，还是**设计行为 + 应用层错误**的组合？
2. 若需要应用层前提，该前提在真实产品中出现的比例有多大？

### 判据

| 情况 | 处理 |
|---|---|
| 组件自身缺陷，无需应用前提 | 直接进 S5，成功率高（案例一：应用只有 `<?php echo "OK\n"; ?>` 也能打穿） |
| 依赖应用层特征（不安全 include、特定入口等） | **先做产品筛查**，再决定是否投入（案例二） |
| 组件侧是设计行为 | **不会有组件 CVE**，归属应挂到应用（见 scoring.md） |

### 案例二为什么必须在 S4 停下先筛查

链条两个前提：① `session.upload_progress` 开启且用文件 session；
② 存在用户可控的 `include()`。

筛查后发现：**前提①几乎免费**（11/11 产品默认满足，是 PHP 官方默认值），
**前提②才是门槛**——12 个真实产品全部缺失。若跳过筛查直接逐个搭靶场，
投入会全部打水漂。

筛查手法（便宜且有效）：

```bash
# 读运行配置，确认前提①
docker exec <c> php -i | grep -E 'session.upload_progress|save_handler'

# 源码 grep 找用户输入直达 include 的汇点，确认前提②
grep -rn 'include\s*(\s*\$\|require\s*(\s*\$' <docroot> --include='*.php' \
  | grep -iE '_GET|_POST|_REQUEST|_COOKIE'
```

**产出**：分诊结论 + 支撑数据（命中数/总数）。**"不可用"的结论同样是有效结论**，
但必须写明是"确认缺失"还是"未能评估"。

## S5 靶场化验证

### 隔离命名空间（必做）

同一台机器上可能有多个靶场并存。用**专属前缀 + 独立端口段**：

| 资源 | 约定 |
|---|---|
| 容器名 | `<前缀>-<版本>`（如 `sp-8234`、`cve-wp`） |
| 端口 | 专属号段（如 192xx–196xx / 181xx） |
| 清理脚本 | **只删自己前缀的容器** |

案例二明确记录了不这样做的后果：`sp_lab_down.sh` 只删 `sp-*`，不会误伤别的项目。

### 固定必要配置

把"缺一不可"的配置写进启动脚本，并单独列表说明"不设会怎样"。案例一的四条：

| 配置 | 值 | 不设的后果 |
|---|---|---|
| `memory_limit` | `8M` | 触发不到 OOM |
| `output_buffering` | `0` | 镜像默认 true 会破坏泄露窗口（0B vs 600000B） |
| `max_input_vars` | 大值 | 默认 1000 截断 513+ 字段的请求 |
| 单 worker prefork | `MaxRequestWorkers 1` | 跨请求命中不同进程，状态不残留 |

### 对照与统计（不可省）

- 漏洞版跑 N 次给成功率
- **修复版跑同样 N 次**，应全部失败
- 两者都记录原始输出

案例一判据极简且好用：**cookie ≈ 32 字节 = 不可用；≈ 600000 字节 = 可打穿。**

**回退**：修复版也成功 → 说明根本不是这个补丁在起作用，回 S1 重新核对版本区间。

## S6 打穿与 exp

真实约束通常不在漏洞本身，而在这些地方：

| 约束 | 处理 |
|---|---|
| 单次命令长度限制 | 两段式 stager（案例一只有 14 字节槽） |
| ASLR 基址假设 | 先读目标 `/proc/<pid>/maps` 核实，不要硬编码（`0x7f` 假定导致 leak 全灭） |
| 入口差异 | 不同入口可能破坏利用窗口（phpMyAdmin 只有 `show_config_errors.php` 可行） |
| 符号/偏移 | 从目标自身提取，不要跨版本复用 |

案例一的两个真实坑（值得当作检查清单）：

1. **模块指针识别**：泄露的是函数内部地址（`base + dtor + 0xb`），不是函数入口。
   用"低 12 位相等"匹配会全灭 → 改为允许小窗口 + 4KB 对齐筛选。
2. **`output_buffering`**：开启时 OOM 被错误处理器捕获，悬空指针不复存在。

**产出**：可重复执行的 exp + 一键脚本（起靶场 / 跑利用 / 清理）。

### 打穿之后：优先交付交互式 shell

拿到 RCE 不等于交付完成。用户通常想**自己敲命令**，所以按这个优先级走：

| 优先级 | 形态 | 何时用 |
|---|---|---|
| 1 | **持久 webshell** | 目标存在可写且可访问的目录 |
| 2 | 逐命令 RCE | 拿不到持久通道时的降级 |

**持久 webshell 的通用做法**：用已确认的 RCE 把一个小 shell 写进**可写目录**，
再从 HTTP 访问它。常见的可写落点：

- bind mount 的 docroot（靶场环境最常见，`/var/www/html` 系列）
- 上传目录、缓存目录、日志目录
- 任何 `www-data` 可写且 Web 可访问的路径

注意区分**可写**与**可访问**：案例一的 php2shell 靶场 docroot 是 `:ro`，
但 `/out` 是可写 bind mount，所以那里只能走「写文件 + 读文件」的通道，拿不到持久 shell。

**降级时必须坦白**，明确告诉用户差额：

```
无持久 webshell 可用，改用逐命令执行 —— 每条命令会重跑利用，
不保留 cd/env 状态
```

**已修复的目标不要给 shell。** 修复对照本来就不该有通道；
给出一个"能用"的 shell 等于伪造结论，比不给更糟。

**交付前必须验证 shell 真能应答**（跑一条 `id` 看回显），不要只看"文件写成功了"。

**清理是义务**：会话结束、重启、异常退出都要移除落下的 shell 文件；
bind mount 场景下它会留在宿主的仓库目录里，容易被误提交。

## S7 结论与边界

三段式，缺一不可：

```markdown
### 已验证
- 具体环境、具体版本、N/N 成功率

### 未验证 / 已知限制
- 单 worker vs 多 worker 的差异
- 未实测的配置（如只测了 8M 没测 128M）
- 需要本地符号、需要特定前提

### 判断指引（给真实环境用）
- 如何自查版本
- 缓解措施 + 官方是否承认其彻底性
```

**最严重的错误**：把单 worker 打通写成"生产可用"。
官方缓解措施几乎总是"降低风险，升级才是彻底方案"，这一句必须原样保留。
